# Recipes

`recipes/SCHEMA.md` is the normative description of the format and is served verbatim by
`GET /v1/recipes/schema`, so keep it exact and example-driven: its readers are AI assistants
writing recipes from it. When a field changes, update SCHEMA.md in the same change.

## Where recipes come from

Roadie ships no recipes. Every recipe starts in the **catalog**, the repo
`outcast1000/roadie-recipes` (one `recipes/<name>.json` per tool, `index.json` generated by its CI).

- **Catalog**: `recipe/catalog.rs` fetches `index.json` and the files it lists from
  raw.githubusercontent.com into `<data>/catalog/` (TTL 6 h; `refresh_if_stale`, forced by
  `roadie tool list --refresh`, `roadie catalog refresh`, `POST /v1/catalog/refresh`). Each file
  must match its index `sha256`, which proves consistency, not authenticity. An entry whose
  `minRoadie` is newer than this build is hidden. The store lists it as `Origin::Catalog`, which is
  **not trusted**: `get_trusted` refuses it, `compare` calls it `New`, and it becomes a user recipe
  only through the user's click (an approved request that brings it, or Trust in the review screen).
  The fetcher is injected (`refresh_with`), so tests never touch the network.
- **User**: `<data>/recipes/<name>.json`. It is a draft the user trusted, a recipe an app brought
  and the user approved (`store::put_trusted(recipe, source)`), or a catalog recipe the user
  approved. The last kind is an envelope `{"source": "catalog", "recipe": …}`, so recipe updates
  keep coming from the catalog. A plain file is the user's own. A user recipe shadows the catalog
  entry of its name, and deleting it gives the name back.
- **Draft**: `<data>/recipes/<name>.draft.json`, wrapped `{"submittedBy", "recipe"}`; not
  installable. `store::trust` rewrites it as a user recipe. A draft owns its name too.
- **Brought**: a recipe in a request (`RequestKind::Install.recipe`, `ReplaceRecipe`), compared by
  `store::compare` (parsed values, so key order does not count). Never on disk until approved.
- **Fixtures**: `recipe/fixtures/` holds test copies of the first three catalog recipes
  (`fixtures::recipe("slskd")`), `cfg(test)` only. They are never listed and never installable.

## Writing one

- Copy the closest catalog recipe. `slskd.json` is the daemon reference (ports, secrets, `$each` over
  consumers, JWT stop chain, `startFailures`); `yt-dlp.json` the simplest cli; `ffmpeg.json`
  shows `htmlIndex` and per-platform `overrides`.
- Connection: `perConsumerKey` gives each approved app its own key (listed in the config with
  `$each: "consumers"`, so every grant re-renders it). `sharedKey` gives every approved app the
  one secret `connection.key` names; offer that secret with `askOnInstall` so an app that already
  has a key can bring it. Either way, apps talk to the tool directly; Roadie never proxies.
- A tool that should own its configuration after install (edited in its own UI) marks its files
  `writeOnce`, and its settings in Roadie close after install. Offer what must be decided up
  front (ports, keys) with `askOnInstall`.
- Prefer upstream checksums (`sumsFile`, `sidecar`); with `none`, say in `notes` that the copy is
  verified by running it.
- Daemons bind `127.0.0.1`. A `files[].content` that binds elsewhere is a recipe the review
  screen should make the user distrust; don't add engine code to "fix" it.
- A setting an installing app should be able to decide goes in `configuration`, named by the
  tool's own key (`shares.directories`) — not as a `config` field plus a placeholder. The recipe's
  `files` keep everything Roadie must control (ports, bindings, keys); an entry can only touch what
  it names. Placement is `recipe::apply_entries`, run by `render_files` after expanding the file.
- Config fields that are secrets are `kind: password, secret: true` and flow to `{secrets.X}`;
  everything else is `{config.X}`. Directories a daemon refuses to start without go in
  `createDirs` or a path field's `createDir`.
- `files[].path` must start with `{data}` — a recipe writes only inside its own data dir.
- Prefer structured `content` over `format: raw`; the emitters quote by construction.

## The engine side (`src-tauri/src/recipe/`)

- `mod.rs` — types (serde, camelCase, `deny_unknown_fields` deliberately **off** so an older
  Roadie reads a newer recipe's additive fields), `validate()` returning
  `Vec<ValidationError {pointer, message}>`, `Platform`, `Recipe::{source_for, archive_for,
  layout_for, binaries, supported_on}`.
- `template.rs` — `{placeholder}` expansion with typed single-placeholder values, `$each`
  (static keys kept), `$if/then/else`; `placeholders()` and `split_filter()` back the validator.
- `emit.rs` — YAML (strings as JSON strings → safe scalars), JSON, env, ini, raw.
- `jsonq.rs` — `$`, `.key`, `[n]`, `[*]`, `..key`.
- `httpsteps.rs` — `send()` and `run_chain()` with captures; `SendError::Unreachable` is the
  signal liveness keys on.

Validation errors are the product: when you add a check, the message must tell an assistant
what to change (`"`{ports.wev}` names nothing this recipe declares"`), and a test asserts the
pointer.
